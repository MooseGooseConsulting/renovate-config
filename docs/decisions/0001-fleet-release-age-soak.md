# ADR 0001: Fleet-wide 4-day release-age soak, failing closed

- Status: accepted (owner decision, 2026-10-21); amended the same day to date GHCR images through the GitHub Packages API ([#27](https://github.com/MooseGooseConsulting/renovate-config/issues/27))
- Applies to: every repository the shared preset reaches

## Context

On 2026-10-21, LiteLLM 1.107.0 was published to PyPI and Docker Hub/GHCR with a credential stealer that ran on every Python start. It was pulled about two hours later ([advisory](https://docs.litellm.ai/blog/security-incident-oct-21-2026)). homelab-next was not affected because its image is pinned by digest. But its Renovate rule set `minimumReleaseAgeBehaviour: timestamp-optional`. GHCR publishes no release dates, so the 4-day soak recorded on that rule never applied, and a poisoned release could have been proposed on the next run.

Facts about Renovate 44.107.0, the runner's pinned version:

- `minimumReleaseAge` holds a release until it is old enough. With `timestamp-required`, the default since v42, an undated release is held indefinitely.
- The docker datasource reads release dates only from Docker Hub. GHCR support ([renovatebot/renovate#39064](https://github.com/renovatebot/renovate/issues/39064)) is unshipped through 44.176.2, the newest release on 2026-10-21; a maintainer's prototype branch (`feat/ghcr-mra`) uses the same GitHub Packages API and has no PR. The OCI `created` annotation is set by the publisher, and maintainers reject it as forgeable; opt-in OCI timestamps ([#43566](https://github.com/renovatebot/renovate/pull/43566)) are unmerged.
- GitHub's `GET /users/{owner}/packages/container/{name}/versions` returns each digest's tags and `created_at`, which GitHub sets when the digest is first pushed. The `/users/` path serves user- and organization-owned packages, public and (with access) private; `/orgs/` serves only organization-owned ones. It needs a token with `read:packages` (or `write:packages`); without one it answers HTTP 403 (the runner's classic PAT on 2026-10-21; 401 with no token at all), which Renovate records only as a `no-result` lookup warning in the report, not in its log. It returns one page of at most 100 versions, newest first, and untagged platform manifests and signatures count toward the 100. A custom datasource cannot page: it fetches one URL, and several `registryUrls` resolve to the first only (custom datasources use the `first` registry strategy, which configuration cannot change).
- Docker Hub refuses anonymous tag paging past page 10. When that happens, Renovate discards every date it fetched ([#46925](https://github.com/renovatebot/renovate/issues/46925)).
- Pin, pinDigest, replacement, lock-file maintenance and rollback updates carry no release date. Range bumps (`rangeStrategy: bump`) and lock-file-only updates are flags on major, minor and patch updates, so they are dated and held like them.
- `python-version`, `java-version`, `dart-version`, `github-runners`, `git-refs` and `git-tags` publish no release dates. A digest update of a floating tag (`latest`, `lts-alpine`) is never dated either, because Renovate 44 has no version to take the date from.
- Pure digest updates are aged against the current version's date at lookup. The branch-stage `renovate/stability-days` check reads a field digest updates never have, so it stays pending forever ([#45236](https://github.com/renovatebot/renovate/issues/45236)).
- `github-tags` dates a tag by its first release, so a force-pushed tag passes at once.
- Lock files are regenerated by the package manager, which re-resolves transitive dependencies to the newest version it allows. Renovate passes the branch's `minimumReleaseAge` to two managers: npm gets `--before=<now minus the age>` ([#42552](https://github.com/renovatebot/renovate/pull/42552)), skipped when `.npmrc` sets `min-release-age` ([#43187](https://github.com/renovatebot/renovate/pull/43187)), and Poetry gets `POETRY_SOLVER_MIN_RELEASE_AGE` ([#43429](https://github.com/renovatebot/renovate/pull/43429)), which Poetry 2.4 and later honour. It passes nothing to uv ([#41654](https://github.com/renovatebot/renovate/issues/41654)), pnpm ([#42145](https://github.com/renovatebot/renovate/pull/42145)), bun, Yarn, Cargo ([#41659](https://github.com/renovatebot/renovate/issues/41659)) or pip ([#41655](https://github.com/renovatebot/renovate/issues/41655)); those apply only their own cooldown setting. Terraform lock-file maintenance takes the newest provider version inside the constraint without an age check.

## Decision

- **The rule.** Major, minor, patch and digest updates wait 4 days after release, with `timestamp-required` stated explicitly. Pin, pinDigest, replacement, lockFileMaintenance and rollback updates are not held, because they carry no date, matching Renovate's own `security:minimumReleaseAge*` presets; range bumps and lock-file-only updates are held with the updates they ride on.
- **GHCR dates.** `default.json` moves third-party `ghcr.io/**` docker dependencies to the `custom.ghcr` custom datasource, which maps the Packages API response to releases (version = tag, `newDigest` = index digest, `releaseTimestamp` = `created_at`) and drops `sha256-*` signature tags. The package name keeps its `ghcr.io/` prefix, so rules that match it by name still match; the datasource strips it in the URL. Versioning stays `docker`. Because rules that run after the override no longer see `docker` as the datasource, the container-images group lists `custom.ghcr` too, and a consumer rule that maps a GHCR image to a Docker Hub mirror must set `overrideDatasource: docker`. Three images push 100 versions within hours, so no release in the page is ever 4 days old, and they stay on the docker datasource (undated, held, counted as such): `astral-sh/uv`, `cloudnative-pg/postgresql` and `renovatebot/renovate` (measured 2026-10-21; [#27](https://github.com/MooseGooseConsulting/renovate-config/issues/27) has the table). The runner probes the Packages API with its token before every run and raises an error annotation and a job-summary section if the token cannot read it; the run continues, because the images then get no updates at all, which is fail-closed.
- **Exemptions.** First-party images on GHCR (`ghcr.io/moosegooseconsulting/**`, `ghcr.io/coldaine/**`) and first-party GitHub actions and releases (`MooseGooseConsulting/**`, `Coldaine/**`, scoped to the GitHub datasources so an unclaimed Docker Hub namespace of the same name stays soaked) are exempt, because this fleet builds them. `github-runners`, `python-version`, `java-version` and `dart-version` are exempt: they name official toolchain releases, and holding them forever would stop the Python patch releases the 2026-10-13 Python rule keeps flowing. Vulnerability-fix PRs keep their bypass.
- **Lock files.** Lock-file maintenance carries `minimumReleaseAge: 4 days`, so Renovate passes the soak to npm and Poetry when it regenerates their lock files. It still holds nothing: lock-file maintenance has no release date, and the stability check is off. Lock-file maintenance runs only for npm, bun, pep621 and poetry, whose regeneration honours a cooldown, and not where a `yarn.lock` or `pdm.lock` is present: the npm and pep621 managers also maintain those, Renovate passes them no cooldown, and Yarn Classic has none (`matchFileNames` matches a package file's lock files). Every other manager's lock files change only with an ordinary update. NuGet is among them: it resolves the lowest applicable version, but a floating version (`1.*`) takes the newest match with no age check, so its maintenance is off too (screen-ingest, the only fleet repository with `packages.lock.json`, pinned exact versions on 2026-10-22). Repositories using uv, pnpm or bun set the 4-day cooldown in their own configuration, which also covers people locking by hand: `[tool.uv] exclude-newer = "4 days"` in `pyproject.toml`, `minimumReleaseAge: 5760` (minutes) in `pnpm-workspace.yaml`, or `minimumReleaseAge = 345600` (seconds) under `[install]` in `bunfig.toml`. npm repositories do not set `.npmrc` `min-release-age` (see Consequences).
- **Status check.** `statusCheckWhen.minimumReleaseAge: never` turns off the stability status check. The gate is the lookup stage: `internalChecksFilter: strict` creates no branch until an update has aged.
- **Runner settings.** The runner sets `dockerMaxPages: 10`, which is a global-only option, and writes a file report. A job-summary step turns it into four counts per repository:
  - **Held, no release date:** waits forever unless the dependency gets a dated source or an exemption. Any count raises a warning annotation.
  - **Held, aging:** under 4 days old, and clears by itself.
  - **Newer releases withheld:** Renovate proposed an older release while newer ones wait. The report does not say whether those are dated, so they are excluded from the undated count. They normally age out.
  - **Lookup warnings.**

  Public repositories are named, checked with the runner's token; private ones are aggregated. Repositories whose visibility lookup fails get a separate "visibility unknown" row and a warning.
- **GHCR lookup warnings.** The job summary adds a column counting lookup warnings that name `custom.ghcr`: a lookup that returned nothing (403 or 401 without packages access, 404 for an unknown name), or a pinned tag that has left the newest 100 versions (`Could not determine new digest`), whose digest updates are lost while newer versioned releases still come through. Each run with any raises a warning annotation.
- **Undated images.** Consumers keep undated images updating by mapping each one to a Docker Hub repository that serves identical index digests, using `overridePackageName`. The mapping is checked per tag before it is added. Images with no such mirror stay held, visibly.

## Consequences

- **Fewer updates.** Non-exempt images on Quay, registry.k8s.io, MCR and GCR, and the three excluded GHCR images, get no version or digest updates unless they are mapped. Floating-tag digests (`node:lts-alpine@sha256:…`) and `git-refs`/`git-tags` dependencies are held forever too; a mapping cannot help them. The remedy is a versioned tag (`node:24.11-alpine@sha256:…`), or a narrow consumer rule with `minimumReleaseAge: null` where the owner accepts the risk. This trades part of North Star G1 ("use Renovate broadly") for supply-chain safety. Under "Quiet, Not Silent", the job summary is what keeps the holds visible, so a broken summary is a policy failure, not cosmetic.
- **GHCR coverage is one page.** An image that pushes 100 versions in under 4 days shows only releases younger than the soak, so it reads as "Held, aging" while it stays that busy; LiteLLM (`berriai/litellm-non_root`), `gethomepage/homepage`, `kenn-io/agentsview`, `dagucloud/dagu` and `tronbyt/server` had such windows for 1% to 37% of the last 90 days (agentsview the most). A consumer can map such an image to a digest-identical Docker Hub repository (homelab-next does for LiteLLM and homepage). A floating tag (`latest`, `beta`) gets no digest update from `custom.ghcr`, because the datasource cannot look up a digest outside its releases; it was held undated before, and now shows as a GHCR lookup warning. A floating version tag such as `2` is dated by the digest that carries it. To measure an image's window: `gh api 'users/OWNER/packages/container/NAME/versions?per_page=100' --jq '.[0].created_at, .[-1].created_at'`.
- **GHCR depends on one token scope.** Removing `read:packages` from `RENOVATE_TOKEN` stops every third-party GHCR update; the probe step reports it. The lookups add at most one GitHub API request per GHCR image per repository to the token's rate limit.
- **Docker Hub coverage is partial.** Dates come from the newest 1,000 tags. A pin older than that loses digest-update dates, though newer versions still arrive. A mapped image depends on its mirror staying digest-identical; if it drifts, a proposed digest may not exist on the original registry.
- **Transitive dependencies are held where the package manager can hold them.** The soak filters only the version Renovate proposes; a regenerated lock file gets whatever the package manager resolves ([discussion #41607](https://github.com/renovatebot/renovate/discussions/41607)). Fixture runs on Renovate 44.107.0 ([#28](https://github.com/MooseGooseConsulting/renovate-config/issues/28)) showed lock-file maintenance without a cooldown pulling caniuse-lite and electron-to-chromium releases under a day old into `package-lock.json` and `bun.lock`, 1.3-day-old ones into `pnpm-lock.yaml` (pnpm 11's built-in 1-day default), and a botocore release hours old into `uv.lock` and `poetry.lock`. An ordinary boto3 update pulled the same botocore into `uv.lock`. With the cooldowns above, every resolved release was over 4 days old, and soaked direct updates (6 and 7 days old) still went through.
- **Consumers must carry the uv, pnpm and bun setting.** A repository without it still gets un-soaked transitive releases from those managers. Adding `exclude-newer` to an existing uv project needs one `uv lock`, so `uv.lock` records `exclude-newer-span`; otherwise `uv sync --locked` fails. A relative `exclude-newer` (`"4 days"`) needs uv 0.9.17 or later; older uv cannot parse the `[tool.uv]` table at all, so `required-version` cannot enforce the floor, and the floor is stated in a comment beside the setting instead.
- **Security fixes younger than 4 days.** Vulnerability PRs bypass Renovate's soak but not a package manager's. pnpm: Renovate adds the fixed version to `minimumReleaseAgeExclude` ([#39168](https://github.com/renovatebot/renovate/issues/39168)). uv and bun: the PR opens with an artifact error naming the cutoff; exempt only the fixed release in that PR. uv: add `exclude-newer-package = { <name> = "<RFC 3339 time just after the fix release's last file upload>" }` and run `uv lock --upgrade-package <name>`; do not use `{ <name> = false }`, which exempts every future release of the package (verified on uv 0.9.17 and 0.13.3 with certifi). Once that release is 4 days old, remove the entry and run `uv lock`. Removing it earlier makes `uv lock` silently downgrade to the vulnerable version, because uv drops a locked release younger than the cutoff (verified with certifi 2026.10.19, the fix for PYSEC-2026-4320). bun: add `<name>@<version>` to `minimumReleaseAgeExcludes`, not a bare package name, and remove it once the release is 4 days old. npm: with `.npmrc` `min-release-age` set, Renovate skips `--before`, npm refuses the version, and Renovate drops the branch with no PR and no warning (debug log only). That would silently delay security fixes, so npm repositories rely on Renovate's `--before` instead. It covers Renovate's lock files, not a person running `npm install`; a per-user `~/.npmrc` with `min-release-age=4` covers hand-run installs without affecting Renovate.
- **Ordinary updates still re-resolve transitives.** For Cargo, Bundler, Composer, Gradle, Terraform, Yarn, PDM and the other managers without a cooldown, turning off lock-file maintenance removes only the weekly full regeneration. An ordinary update still runs the package manager, which may add a transitive release published minutes earlier; only the version Renovate proposes is soaked.
- **npm's `--before` can fall back.** When npm fails with ETARGET because a package already in the lock file is newer than the `--before` cutoff (for example after a security fix or a hand-run install), Renovate 44.107.0 retries without `--before` (`lib/modules/manager/npm/post-update/npm.ts`) and still commits the lock file, so that regeneration is not soaked. It logs a WARN ("npm `--before` could not be enforced …") and adds an artifact notice to the PR. The WARN appears in the runner's job-summary problem counts. The gap closes once the newer locked package is itself older than 4 days.
- **Not covered.** Yarn Classic has no cooldown (no fleet repository uses Yarn; its lock-file maintenance is off). Requirements files are not re-resolved. Go modules use minimal version selection, so an update adds only versions the updated module already required. NuGet floating versions (`1.*`) still re-resolve unsoaked on an ordinary update.
- **No fast lane for images.** GitHub advisories do not cover container images, so an urgent image fix needs a narrow consumer rule with `minimumReleaseAge: null`.
- **Other runners.** A consumer that runs Renovate outside this runner must set `dockerMaxPages` itself.
- **The page cap is global.** Renovate 44 always pages GHCR, Quay, cgr.dev and Red Hat registries fully. Other non-Docker-Hub registries stop at 10 pages, but their images have no dates and are held regardless. An image exempted with `minimumReleaseAge: null` on an oldest-first registry such as lscr.io may miss its newest tags; give such a repository its own runner setting if that arises.

## Revisit when

- Renovate dates GHCR images natively (#39064): replace `custom.ghcr` with it, after checking it pages further than 100 versions. Or opt-in OCI timestamps (#43566) merge.
- An excluded GHCR image slows down (re-measure its window), or the GHCR lookup-warning count stays up for an image that is not a floating tag.
- Renovate fixes #45236 or #46925.
- Renovate passes the age to uv (#41654) or pnpm (#42145), or writes npm `min-release-age-exclude` (npm 12) or bun `minimumReleaseAgeExcludes` entries for security fixes; the last would let npm repositories carry their own cooldown.
- The job summary shows undated holds growing without mappings being added, or a repository's "newer releases withheld" count staying up across runs (inspect it with a local dry run; it may hide undated releases).
