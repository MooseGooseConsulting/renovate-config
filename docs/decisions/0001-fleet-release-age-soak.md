# ADR 0001: Fleet-wide 4-day release-age soak (dated sources fail closed)

- Status: accepted (owner decision, 2026-10-21); amended the same day to date GHCR images through the GitHub Packages API ([#27](https://github.com/MooseGooseConsulting/renovate-config/issues/27)); amended 2026-10-22 so undated sources come as ordinary PRs instead of being held forever, and the runner's job summary and the Docker Hub mappings are removed ([#33](https://github.com/MooseGooseConsulting/renovate-config/issues/33))
- Applies to: every repository the shared preset reaches

## Context

On 2026-10-21, LiteLLM 1.107.0 was published to PyPI and Docker Hub/GHCR with a credential stealer that ran on every Python start. It was pulled about two hours later ([advisory](https://docs.litellm.ai/blog/security-incident-oct-21-2026)). homelab-next was not affected because its image is pinned by digest. But its Renovate rule set `minimumReleaseAgeBehaviour: timestamp-optional`. GHCR publishes no release dates, so the 4-day soak recorded on that rule never applied, and a poisoned release could have been proposed on the next run.

Facts about Renovate 44.107.0, the runner's pinned version:

- `minimumReleaseAge` holds a release until it is old enough. With `timestamp-required`, the default since v42, an undated release is held indefinitely.
- The docker datasource reads release dates only from Docker Hub. GHCR support ([renovatebot/renovate#39064](https://github.com/renovatebot/renovate/issues/39064)) is unshipped through 44.176.2, the newest release on 2026-10-21; a maintainer's prototype branch (`feat/ghcr-mra`) uses the same GitHub Packages API and has no PR. The OCI `created` annotation is set by the publisher, and maintainers reject it as forgeable; opt-in OCI timestamps ([#43566](https://github.com/renovatebot/renovate/pull/43566)) are unmerged.
- GitHub's `GET /users/{owner}/packages/container/{name}/versions` returns each digest's tags and `created_at`, which GitHub sets when the digest is first pushed. The `/users/` path serves user- and organization-owned packages, public and (with access) private; `/orgs/` serves only organization-owned ones. It needs a token with `read:packages` (or `write:packages`); without one it answers HTTP 403 (the runner's classic PAT on 2026-10-21; 401 with no token at all), which Renovate records only as a `no-result` lookup warning in the report, not in its log. It returns one page of at most 100 versions, newest first, and untagged platform manifests and signatures count toward the 100. A custom datasource cannot page: it fetches one URL, and several `registryUrls` resolve to the first only (custom datasources use the `first` registry strategy, which configuration cannot change).
- Docker Hub refuses anonymous tag paging past page 10. When that happens, Renovate discards every date it fetched ([#46925](https://github.com/renovatebot/renovate/issues/46925)).
- Pin, pinDigest, replacement, lock-file maintenance and rollback updates carry no release date. Range bumps (`rangeStrategy: bump`) and lock-file-only updates are flags on major, minor and patch updates, so they are dated and held like them.
- `java-version`, `dart-version`, `github-runners`, `git-refs` and `git-tags` publish no release dates. `python-version` takes them from python.org's release feed (checked 2026-10-22). A digest update of a floating tag (`latest`, `lts-alpine`) is never dated, because Renovate 44 has no version to take the date from.
- With `timestamp-optional`, an update that has a date still waits until it is old enough; one without a date is not held (`lib/workers/repository/process/lookup/filter-checks.ts` and `digest.ts`).
- Pure digest updates are aged against the current version's date at lookup. The branch-stage `renovate/stability-days` check reads a field digest updates never have, so it stays pending forever ([#45236](https://github.com/renovatebot/renovate/issues/45236)).
- `github-tags` dates a tag by its first release, so a force-pushed tag passes at once.
- Lock files are regenerated by the package manager, which re-resolves transitive dependencies to the newest version it allows. Renovate passes the branch's `minimumReleaseAge` to two managers: npm gets `--before=<now minus the age>` ([#42552](https://github.com/renovatebot/renovate/pull/42552)), skipped when `.npmrc` sets `min-release-age` ([#43187](https://github.com/renovatebot/renovate/pull/43187)), and Poetry gets `POETRY_SOLVER_MIN_RELEASE_AGE` ([#43429](https://github.com/renovatebot/renovate/pull/43429)), which Poetry 2.4 and later honour. It passes nothing to uv ([#41654](https://github.com/renovatebot/renovate/issues/41654)), pnpm ([#42145](https://github.com/renovatebot/renovate/pull/42145)), bun, Yarn, Cargo ([#41659](https://github.com/renovatebot/renovate/issues/41659)) or pip ([#41655](https://github.com/renovatebot/renovate/issues/41655)); those apply only their own cooldown setting. Terraform lock-file maintenance takes the newest provider version inside the constraint without an age check.

## Decision

- **The rule.** Major, minor, patch and digest updates wait 4 days after release, with `timestamp-required` stated explicitly for dated sources: npm, PyPI, crates.io, GitHub releases and tags, Docker Hub and third-party GHCR images (`custom.ghcr`). Pin, pinDigest, replacement, lockFileMaintenance and rollback updates are not held, because they carry no date, matching Renovate's own `security:minimumReleaseAge*` presets; range bumps and lock-file-only updates are held with the updates they ride on.
- **Undated sources (amended 2026-10-22).** The owner's direction is that no update is held forever. Three rules set `timestamp-optional` for sources that publish no dates: the `git-refs`, `git-tags`, `github-runners`, `python-version`, `java-version` and `dart-version` datasources; the docker datasource for every registry but Docker Hub (any name whose first part is a host other than `docker.io`, `index.docker.io` or `registry-1.docker.io`); and digest updates of a tag that is not a version (`latest`, `lts-alpine`, a branch name). They still wait 4 days when a date exists; otherwise they come as ordinary PRs, which are never automerged, for review. The docker rule sits after the GHCR rule, so images moved to `custom.ghcr` keep `timestamp-required`.
- **GHCR dates.** `default.json` moves third-party `ghcr.io/**` docker dependencies to the `custom.ghcr` custom datasource, which maps the Packages API response to releases (version = tag, `newDigest` = index digest, `releaseTimestamp` = `created_at`) and drops `sha256-*` signature tags. The package name keeps its `ghcr.io/` prefix, so rules that match it by name still match; the datasource strips it in the URL. Versioning stays `docker`. Because rules that run after the override no longer see `docker` as the datasource, the container-images group lists `custom.ghcr` too, and a consumer rule that maps a GHCR image to a Docker Hub mirror must set `overrideDatasource: docker`. Three images push 100 versions within hours, so no release in the page is ever 4 days old, and they stay on the docker datasource, undated, where they come as ordinary PRs: `astral-sh/uv`, `cloudnative-pg/postgresql` and `renovatebot/renovate` (measured 2026-10-21; [#27](https://github.com/MooseGooseConsulting/renovate-config/issues/27) has the table). The runner probes the Packages API with its token before every run and raises an error annotation if the token cannot read it; the run continues, because the images then get no updates at all, which is fail-closed. Each such image is listed on the repository's Dependency Dashboard as a failed lookup.
- **Exemptions.** First-party GitHub actions and releases (`MooseGooseConsulting/**`, `Coldaine/**`, scoped to the GitHub datasources so an unclaimed Docker Hub namespace of the same name stays soaked) are exempt, because this fleet builds them. First-party GHCR images and the runtime version lists needed exemptions only while undated sources were held; the 2026-10-22 amendment removed those two rules, since the undated-source rules cover them. Vulnerability-fix PRs keep their bypass.
- **Lock files.** Lock-file maintenance carries `minimumReleaseAge: 4 days`, so Renovate passes the soak to npm and Poetry when it regenerates their lock files. It still holds nothing: lock-file maintenance has no release date, and the stability check is off. Lock-file maintenance runs only for npm, bun, pep621 and poetry, whose regeneration can honour a cooldown, and not where a `yarn.lock` or `pdm.lock` is present: the npm and pep621 managers also maintain those, Renovate passes them no cooldown, and Yarn Classic has none (`matchFileNames` matches a package file's lock files). Every other manager's lock files change only with an ordinary update. NuGet is among them: it resolves the lowest applicable version, but a floating version (`1.*`) takes the newest match with no age check, so its maintenance is off too (screen-ingest, the only fleet repository with `packages.lock.json`, pinned exact versions on 2026-10-22). Only npm's `package-lock.json` and Poetry get the cooldown from Renovate, and Poetry only from 2.4.0: Renovate runs the Poetry version named in the `poetry.lock` header (`lib/modules/manager/poetry/artifacts.ts`), and older Poetry ignores `POETRY_SOLVER_MIN_RELEASE_AGE`, so a `poetry.lock` from Poetry 1.x–2.3 must be re-locked with Poetry 2.4 or later. For uv, pnpm and bun the cooldown is consumer-supplied, and this preset neither requires nor checks it: a repository without the setting still gets weekly maintenance that can pull a transitive release minutes old (see Consequences). Repositories using uv, pnpm or bun set the 4-day cooldown in their own configuration, which also covers people locking by hand: `[tool.uv] exclude-newer = "4 days"` in `pyproject.toml`, `minimumReleaseAge: 5760` (minutes) in `pnpm-workspace.yaml`, or `minimumReleaseAge = 345600` (seconds) under `[install]` in `bunfig.toml`. npm repositories do not set `.npmrc` `min-release-age` (see Consequences).
- **Status check.** `statusCheckWhen.minimumReleaseAge: never` turns off the stability status check. The gate is the lookup stage: `internalChecksFilter: strict` creates no branch until an update has aged.
- **Runner settings.** The runner sets `dockerMaxPages: 10`, which is a global-only option. Its own image comes from Docker Hub (`renovate-image: docker.io/renovate/renovate`), so the runner's updates are dated; `validate.yml` validates with the same image and release, and `renovate.json` groups the two pins into one PR.
- **Where held updates show.** Each repository's Dependency Dashboard lists updates still waiting out the 4 days ("Pending Status Checks") and lookups that failed. The runner writes no report and no held-update summary (removed 2026-10-22 as tooling no reference configuration has); the only thing it adds to its job summary is the GHCR probe's note when the token cannot read packages. Renovate logs a WARN each run in which `timestamp-optional` lets an undated update through, and the dashboard would list it under "Repository Problems" in every repository with undated dependencies. That is expected here, so `default.json` remaps exactly that message to INFO with `logLevelRemap`, as Renovate's [minimum release age docs](https://docs.renovatebot.com/key-concepts/minimum-release-age/) suggest, and real warnings stay visible.
- **Images with a Docker Hub copy.** An image whose Docker Hub repository serves the same index digests can simply be referenced there, so Renovate dates it on Docker Hub. homelab-next did this for LiteLLM and homepage on 2026-10-22, after checking the pinned digests on both registries.

## Consequences

- **Undated updates are not soaked.** Images on Quay, registry.k8s.io, MCR, GCR and lscr.io, the three excluded GHCR images, floating-tag digests (`node:lts-alpine@sha256:…`) and `git-refs`/`git-tags` dependencies come as PRs as soon as they are published. Review is the check for them: Renovate never automerges, and the reviewing agent should treat a just-published undated release with the caution the soak gives dated ones. A versioned tag (`node:24.11-alpine@sha256:…`) on Docker Hub, or the Docker Hub copy of an image, brings it under the soak. Until 2026-10-22 these updates were held forever, which hid them instead of reviewing them.
- **GHCR coverage is one page.** An image that pushes 100 versions in under 4 days shows only releases younger than the soak, so it waits while it stays that busy; LiteLLM (`berriai/litellm-non_root`), `gethomepage/homepage`, `kenn-io/agentsview`, `dagucloud/dagu` and `tronbyt/server` had such windows for 1% to 37% of the last 90 days (agentsview the most). A consumer can reference such an image's digest-identical Docker Hub repository instead (homelab-next does for LiteLLM and homepage). A floating tag (`latest`, `beta`) gets no digest update from `custom.ghcr`, because the datasource cannot look up a digest outside its releases; the lookup warning shows on the Dependency Dashboard. A floating version tag such as `2` is dated by the digest that carries it. To measure an image's window: `gh api 'users/OWNER/packages/container/NAME/versions?per_page=100' --jq '.[0].created_at, .[-1].created_at'`.
- **GHCR depends on one token scope.** Removing `read:packages` from `RENOVATE_TOKEN` stops every third-party GHCR update; the probe step reports it. (On 2026-10-22 the token still lacked the scope; adding it is an owner action.) The lookups add at most one GitHub API request per GHCR image per repository to the token's rate limit.
- **Docker Hub coverage is partial.** Dates come from the newest 1,000 tags. A versioned pin older than that loses digest-update dates, so its digest updates wait (newer versions still arrive). This is the one hold left that does not clear by itself; moving the pin to a newer version clears it.
- **Transitive dependencies are held where the package manager can hold them.** The soak filters only the version Renovate proposes; a regenerated lock file gets whatever the package manager resolves ([discussion #41607](https://github.com/renovatebot/renovate/discussions/41607)). Fixture runs on Renovate 44.107.0 ([#28](https://github.com/MooseGooseConsulting/renovate-config/issues/28)) showed lock-file maintenance without a cooldown pulling caniuse-lite and electron-to-chromium releases under a day old into `package-lock.json` and `bun.lock`, 1.3-day-old ones into `pnpm-lock.yaml` (pnpm 11's built-in 1-day default), and a botocore release hours old into `uv.lock` and `poetry.lock`. An ordinary boto3 update pulled the same botocore into `uv.lock`. With the cooldowns above, every resolved release was over 4 days old, and soaked direct updates (6 and 7 days old) still went through.
- **Consumers must carry the uv, pnpm and bun setting, and a Poetry 2.4+ lock.** A repository without it still gets un-soaked transitive releases from those managers, including from weekly lock-file maintenance, which stays on for them. The preset does not check for the setting. On 2026-10-22 every fleet repository with a `uv.lock`, `pnpm-lock.yaml`, `bun.lock` or `poetry.lock` had a consumer PR adding it (ColdVault's re-locks `poetry.lock` with Poetry 2.5.1); a new repository needs the same. Adding `exclude-newer` to an existing uv project needs one `uv lock`, so `uv.lock` records `exclude-newer-span`; otherwise `uv sync --locked` fails. A relative `exclude-newer` (`"4 days"`) needs uv 0.9.17 or later; older uv cannot parse the `[tool.uv]` table at all, so `required-version` cannot enforce the floor, and the floor is stated in a comment beside the setting instead.
- **Security fixes younger than 4 days.** Vulnerability PRs bypass Renovate's soak but not a package manager's. pnpm: Renovate adds the fixed version to `minimumReleaseAgeExclude` ([#39168](https://github.com/renovatebot/renovate/issues/39168)). uv and bun: the PR opens with an artifact error naming the cutoff; exempt only the fixed release in that PR. uv: add `exclude-newer-package = { <name> = "<RFC 3339 time just after the fix release's last file upload>" }` and run `uv lock --upgrade-package <name>`; do not use `{ <name> = false }`, which exempts every future release of the package (verified on uv 0.9.17 and 0.13.3 with certifi). Once that release is 4 days old, remove the entry and run `uv lock`. Removing it earlier makes `uv lock` silently downgrade to the vulnerable version, because uv drops a locked release younger than the cutoff (verified with certifi 2026.10.19, the fix for PYSEC-2026-4320). bun: add `<name>@<version>` to `minimumReleaseAgeExcludes`, not a bare package name, and remove it once the release is 4 days old. npm: with `.npmrc` `min-release-age` set, Renovate skips `--before`, npm refuses the version, and Renovate drops the branch with no PR and no warning (debug log only). That would silently delay security fixes, so npm repositories rely on Renovate's `--before` instead. It covers Renovate's lock files, not a person running `npm install`; a per-user `~/.npmrc` with `min-release-age=4` covers hand-run installs without affecting Renovate.
- **Ordinary updates still re-resolve transitives.** For Cargo, Bundler, Composer, Gradle, Terraform, Yarn, PDM and the other managers without a cooldown, turning off lock-file maintenance removes only the weekly full regeneration. An ordinary update still runs the package manager, which may add a transitive release published minutes earlier; only the version Renovate proposes is soaked.
- **npm's `--before` can fall back.** When npm fails with ETARGET because a package already in the lock file is newer than the `--before` cutoff (for example after a security fix or a hand-run install), Renovate 44.107.0 retries without `--before` (`lib/modules/manager/npm/post-update/npm.ts`) and still commits the lock file, so that regeneration is not soaked. It logs a WARN ("npm `--before` could not be enforced …") and adds an artifact notice to the PR. The gap closes once the newer locked package is itself older than 4 days.
- **Not covered.** Yarn Classic has no cooldown (no fleet repository uses Yarn; its lock-file maintenance is off). Requirements files are not re-resolved. Go modules use minimal version selection, so an update adds only versions the updated module already required. NuGet floating versions (`1.*`) still re-resolve unsoaked on an ordinary update.
- **No fast lane for images.** GitHub advisories do not cover container images, so an urgent image fix needs a narrow consumer rule with `minimumReleaseAge: null`.
- **Other runners.** A consumer that runs Renovate outside this runner must set `dockerMaxPages` itself.
- **The page cap is global.** Renovate 44 always pages GHCR, Quay, cgr.dev and Red Hat registries fully. Other non-Docker-Hub registries stop at 10 pages; their images have no dates either way. An image on an oldest-first registry such as lscr.io may miss its newest tags; give such a repository its own runner setting if that arises.

## Revisit when

- Renovate dates GHCR images natively (#39064): replace `custom.ghcr` with it, after checking it pages further than 100 versions, and decide again whether first-party GHCR images should skip the 4 days (they would start to wait). Or opt-in OCI timestamps (#43566) merge.
- An excluded GHCR image slows down (re-measure its window), or the GHCR lookup-warning count stays up for an image that is not a floating tag.
- Renovate fixes #45236 or #46925.
- Renovate passes the age to uv (#41654) or pnpm (#42145), or writes npm `min-release-age-exclude` (npm 12) or bun `minimumReleaseAgeExcludes` entries for security fixes; the npm exclusion would let npm repositories carry their own cooldown.
- A repository's Dependency Dashboard keeps listing the same update under "Pending Status Checks" across several weekly runs (inspect it with a local dry run).
